Customer 360 Assistant

Source on GitHub

Build the engagement layer once. Let one agent act across all your systems of record.

With Customer 360 Assistant, people ask in Microsoft Teams. One Microsoft Foundry agent routes each request to the right tool, and every action runs as the signed-in user, with their own permissions in each system.

Watch the 2:40 story Deploy the sample

Customer 360 Assistant is an open-source reference implementation. Salesforce and ServiceNow are working examples; Jira, SAP, Workday and your own APIs are not included and follow the same pattern.

One agent routes every request.

A Microsoft Foundry agent understands what the person needs, chooses the tools, correlates answers across systems and drafts the update. The same agent serves every host, and every read and write uses the asker's own access.

Acts as the user, never as a super-user.

The agent holds no shared credential for your systems. It carries the signed-in user's identity, and each system decides what that person may see and change.

Identity gateway

    Sign in once

    Alice signs in to Teams with her work account (Microsoft Entra ID).

  2. 2

    Consent once per system, by design

    Standard OAuth consent the first time the agent reaches a system; a known platform issue can ask again after about an hour.

  3. 3

    The gateway swaps the token

    Azure API Management validates Alice's token, finds her account in each system and gets a token issued to Alice.

  4. 4

No shared credential touches business data. A minimal-access service account only maps Alice to her Salesforce user, and each per-user token exchange appears in Salesforce Login History.

Identity propagation stops privilege escalation, but it cannot stop an agent from misreading intent, so keep confirmations for destructive actions (what it does not protect against).

Why meta-tools instead of one tool per object?

Many MCP servers define one tool per object, so every new object means new code and a longer tool list. A meta-tool server works like a shell: the agent discovers objects, learns their fields and builds the query itself, with the user's own access. Seven generic tools reach the standard and custom objects the user can see, and the list stays the same whatever the size of the org. Read the pattern.

What's in the box.

In this repository

  • Salesforce meta-tool server. Seven tools: discover objects, describe fields, query, search, write and run approvals, plus whoami.
  • Identity gateway. Azure API Management policies for the three-phase on-behalf-of (OBO) exchange.
  • Foundry agents. salesforce-assistant and customer360-assistant, wired through OAuth2 identity-passthrough connections.
  • Engagement. A web chat app, a Teams app for your org catalog, and Microsoft 365 Copilot through Foundry publishing.
  • Delivery. Bicep and azd, Salesforce org setup scripts, demo-data seeding and end-to-end tests.

The two-repo Customer 360 demo

  • snow-meta-tool. ServiceNow tools with the same pattern and the same identity flow.
  • Correlated demo data. Accounts, opportunities, cases and incidents that line up across both systems.

A reference implementation, not a product. It runs on demo data and has not been audited for production. Read the scope and limitations and the known platform issues before you adapt it.

For architects and developers.

Infrastructure as code, the gateway policies, the tool server and the agents are all in the repository. With the prerequisites in place, one command deploys the stack.

Deploy the Salesforce side

Prerequisites: a certificate, the Salesforce org setup, an Entra app for the OAuth2 connection and identity mapping. The installation guide walks through each one.

# after the prerequisites in docs/installation.md
azd env new obo
azd env set SF_INSTANCE_URL "https://your-org.my.salesforce.com"
azd env set SF_CONNECTED_APP_CLIENT_ID "<consumer-key>"
azd env set SF_SERVICE_ACCOUNT_USERNAME "<svc-user>"
azd env set MCP_OAUTH_CLIENT_ID "<mcp-oauth-app-id>"
azd env set MCP_OAUTH_CLIENT_SECRET "<secret>"
azd up
